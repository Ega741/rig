# hashmine — дизайн

- Дата: 2026-09-14
- Статус: черновик, ждёт ревью. Код не начат.
- Имя проекта — **Rig**, тикер `$RIG` (выбрано 2026-09-14). `hashmine` — прежнее рабочее имя, осталось в имени контракта `HashMine`, в именах файлов спеки/планов и крейта. Лого и описание токена решаются до лаунча (§8).

## 1. Что строим

Токен на Robinhood Chain, выпущенный через лаунчпад PONS, и механика «подключил видеокарту в браузере → майнишь токен». Без NFT. Майнеры получают токены, купленные на рынке за комиссии с торговли этим же токеном.

Цель — хайп и число майнеров. Главная метрика: число уникальных `beneficiary` с ≥1 принятой шарой за сутки (из событий `ShareBatch`). Вторичная — суточный оборот токена.

### 1.1 Принятые решения

| Вопрос | Решение |
|---|---|
| Сеть | Robinhood Chain: mainnet 4663, testnet 46630 |
| Лаунч | PONS V2, launch config 0 |
| Комиссия для трейдера | 3% = 1% базовой комиссии PONS + 2% creator tax (`creatorTaxBps = 200`) |
| NFT | Нет |
| Источник наград | Только выкуп токена на наши комиссии. Резерва и аллокации нет |
| Доля команды | 0%. Всё, что приходит, идёт на выкуп для майнеров |
| Модель наград | Раунды, награда пропорциональна работе |
| Майнер | Только браузер (WebGPU + WASM). CUDA/CLI в v1 не входит |
| Админ | Единственная админ-возможность: миграция получателя комиссий с таймлоком 7 дней (§4.3) |
| Репо | `~/Desktop/rig`, отдельный git |

### 1.2 Что взято у hashcats.fun и что нет

Взято:
- keccak256-PoW в браузере;
- адрес получателя внутри хэша, поэтому решение не украсть;
- движки WebGPU + WASM, находки GPU перепроверяются на CPU;
- челлендж зависит от предыдущей работы, майнить впрок нельзя.

Не взято:
- NFT;
- платный вход (entry price);
- «рента» ранним держателям из платежей поздних: при такой структуре доход ранних оплачивают только новые участники;
- стрик и сложность «победитель забирает всё».

Код майнеров hashcats не используется: у `kaoscodes/hashcats-headless` и `asbryx/hashcats-cuda-miner` нет лицензии (GitHub API, 2026-09-14).

## 3. Архитектура

```
трейдеры ──3%──► PONS curve / хук ──2.7% в ETH──► fee escrow
                                                      │ claim()
                                                      ▼
                        PonsTreasury.harvest() ── покупает токен ──► HashMine (пул наград)
                                                                         │ 0.48% пула за активный раунд
                                                                         ▼
                               браузерный майнер ── submit(шары) ──► доли по работе ──► claim()
```

У каждого компонента одна обязанность:

| Компонент | Обязанность | Знает про |
|---|---|---|
| `contracts/src/PonsTreasury.sol` | Запускает токен через PONS, собирает комиссии, покупает токен, мигрирует получателя | PONS, Uniswap v4, адрес `HashMine` |
| `contracts/src/HashMine.sol` | Раунды, проверка шар, распределение наград, claim | Только ERC-20 токен |
| `web/` | Браузерный майнер и статистика | ABI `HashMine` и `PonsTreasury` |

`HashMine` про PONS не знает: пул наград — это его баланс токена за вычетом зарезервированного. Любой перевод токена на `HashMine`, выкуп или донат, пополняет пул. На testnet `HashMine` работает с мок-токеном без PONS.

## 4. PonsTreasury

> **Ревизия 2026-09-14 (вечер).** Решение пользователя: награда майнерам — не выкупленный токен, а сами комиссии в ETH. Выкуп убран целиком; `HashMine` держит пул в ETH. Токен запускает пользователь с кошелька на сайте PONS, контракт его не запускает.

### 4.1 Роль

`PonsTreasury` — получатель creator-fee токена. Он ничего не покупает и не свопит: всё, что пришло, уходит в `HashMine`. Функций вывода ETH или токенов у владельца нет.

Конструктор: `(initialOwner, factory, hashMine)`. `memeHook` и `feeEscrow` читаются из фабрики.

### 4.2 Привязка к токену: `adopt(token)`

`onlyOwner`, один раз. Порядок на мейннете:

1. Деплой `HashMine` и `PonsTreasury` (до запуска токена — адрес treasury нужен заранее).
2. Пользователь запускает токен на PONS со своего кошелька (creatorTaxBps = 200, buyback выключен, пара — ETH).
3. С того же кошелька: `factory.transferCreatorFeeRecipient(token, treasury)` (или сразу указать treasury получателем при запуске, если сайт PONS это позволяет).
4. `treasury.adopt(token)`. Контракт проверяет по фабрике: запуск существует, `creatorFeeRecipient == treasury`, `pairToken == 0` (комиссии в ETH). Иначе revert — чужой или не-ETH токен привязать нельзя.

### 4.3 harvest()

Вызывать может кто угодно, без ограничений по частоте (без покупки нечего защищать от сэндвичей).

1. До graduation: `curve.sweepFees(0)` в `try/catch`.
2. После graduation: `memeHook.sweepPoolFees(poolId, 0, 0)` в `try/catch`. Комиссии в самом токене конвертирует в ETH оператор PONS (замер в §2), после чего они появляются в escrow.
3. `feeEscrow.claim()` в `try/catch`.
4. Весь `address(this).balance` переводится в `HashMine` низкоуровневым `call`; неудача — revert `TransferFailed`.
5. Эмитит `Harvested(forwarded, phase)`.

Проверено форк-тестами против настоящего PONS (блок 62 704 000): покупка на 1 ETH → `harvest()` → ровно 0.027 ETH в `HashMine`; после graduation — комиссии продаж уходят без оператора, комиссии покупок (в токене) — после конвертации оператором.

### 4.4 Миграция получателя комиссий

Нужна, чтобы из-за бага в `HashMine` или `PonsTreasury` комиссии не уходили навсегда в сломанный контракт.

- `proposeMigration(newRecipient)` — `onlyOwner`, выставляет `eta = now + 7 дней`.
- `executeMigration()` — `onlyOwner`, работает в окне `[eta, eta + 3 дня]`, вызывает `factory.transferCreatorFeeRecipient(token, newRecipient)`. Требует `adopt`.
- `cancelMigration()` — `onlyOwner`.
- `renounceOwnership()` делает контракт полностью неизменяемым.

## 5. HashMine

### 5.1 Параметры

`roundLength`, `releaseBps`, `targetShares` и `minDifficulty` передаются в конструктор и хранятся как immutable. В тестах они маленькие, чтобы шары находились быстро; `PonsTreasury` передаёт production-значения из таблицы. `MAX_DIFFICULTY` и `MAX_NONCES` — константы контракта.

| Параметр | Значение | Смысл |
|---|---|---|
| `ROUND_LENGTH` | 600 с | Длина раунда |
| `RELEASE_BPS` | 48 | 0.48% пула за активный раунд; половина пула уходит за 144 раунда ≈ 24 ч |
| `TARGET_SHARES` | 4096 | Целевое число шар на раунд |
| `MIN_DIFFICULTY` | 20 бит | Нижний порог сложности шары |
| `MAX_DIFFICULTY` | 96 бит | Верхний порог, защита от переполнения работы |
| `MAX_NONCES` | 64 | Максимум шар в одной транзакции |
| `GENESIS` | `block.timestamp` деплоя | Начало раунда 1 |

Значения стартовые. До деплоя в mainnet их проверяет симуляция (§7, п. 6), менять — через правку этой спеки.

### 5.2 Раунды и челлендж

- Раунд `r ≥ 1` длится `[GENESIS + (r−1)·ROUND_LENGTH, GENESIS + r·ROUND_LENGTH)`. Шара принимается только для текущего раунда; граница строгая, грейс-периода нет.
- **Активный раунд** — раунд, в котором принята хотя бы одна шара.
- `seed(k)` — хэш последней принятой шары активного раунда `k`.
- **Якорь раунда `r`** — последний активный раунд `a < r`. Если такого нет, якорем служит генезис: `challenge(0) = keccak256(abi.encode(address(this), block.chainid, GENESIS))`, `seed(0) = 0`, `work(0) = 0`.
- `challenge(r) = keccak256(abi.encode(challenge(a), seed(a), r))`.

Челлендж раунда `r` становится известен не позже конца раунда `r−1`. Грейса нет, так что `seed` и работа якоря к этому моменту окончательные. Пока кто-то майнит, раунд впрок не посчитать.

### 5.3 Шара

- Хэш: `h = keccak256(abi.encodePacked(beneficiary, challenge(r), nonce))`, 20 + 32 + 32 = 84 байта.
- Шара сложности `D` валидна, если `uint256(h) >> (256 − D) == 0`.
- Шаре засчитывается работа `2^D`, где `D` — заявленная сложность, а не фактическое число нулевых бит: матожидание `2^(фактические биты)` бесконечно.
- Минимальная сложность раунда: `minDifficulty(r) = clamp(bits(work(a)) − (r − 1 − a), MIN_DIFFICULTY, MAX_DIFFICULTY)`. Здесь `bits(W) = ceil(log2(W / TARGET_SHARES))`, и `bits(W) = 0` при `W ≤ TARGET_SHARES`. Если прошлый раунд активен (`a = r − 1`), сдвиг равен 0; за каждый пустой раунд порог падает на 1 бит.

### 5.4 submit

```solidity
function submit(address beneficiary, uint256 round, uint8 difficulty, uint256[] calldata nonces) external;
```

Проверки (любая неудача — revert):
1. `round == currentRound()`.
2. `minDifficulty(round) ≤ difficulty ≤ MAX_DIFFICULTY`.
3. `1 ≤ nonces.length ≤ MAX_NONCES`.
4. `nonces` строго возрастают. Если `miner.round == round`, то ещё и `nonces[0] > miner.lastNonce`.
5. Каждый `h` валиден для `difficulty`.

Эффекты:
1. Если это первая шара раунда: закрыть предыдущий активный раунд (§5.5) и сохранить `challenge(round)`.
2. Если `miner.round < round` и `miner.work > 0`: рассчитать майнера по его раунду (§5.5) и обнулить `miner.work`.
3. `miner.round = round`, `miner.lastNonce = nonces[len − 1]`, `miner.work += len · 2^difficulty`.
4. `work(round) += len · 2^difficulty`, `seed(round) = h` последней шары батча.
5. Эмитит `ShareBatch(beneficiary, round, difficulty, len, len · 2^difficulty, h)`.

`msg.sender` не проверяется: отправлять может кто угодно (сессионный ключ, релейер), а работа всегда зачисляется `beneficiary`, зашитому в хэш. Перехваченная транзакция ничего не даёт: она зачисляет ту же работу тому же адресу, а повтор отсекает проверка nonce.

### 5.5 Закрытие раунда, расчёт и claim

- Инвариант: незакрытым может быть только последний активный раунд.
- **Закрытие раунда `k`** — при первой шаре более позднего раунда или при `claim`, если `k` уже кончился:
  - `release = (address(this).balance − reserved) · RELEASE_BPS / 10000` (пул — ETH, ревизия §4);
  - `rewardPerWork(k) = mulDiv(release, 1e36, work(k))`;
  - `reserved += release`;
  - эмитит `RoundClosed(k, work(k), release)`.
- Пустые раунды ничего не выпускают, и пропущенные выпуски не копятся: после простоя первый активный раунд получает те же 0.48% пула.
- **Расчёт майнера:** `claimable += mulDiv(miner.work, rewardPerWork(miner.round), 1e36)`.
- **`claim(beneficiary)`** вызывает кто угодно, выплата идёт `beneficiary` низкоуровневым `call` с ETH; если получатель не принимает ETH — revert `TransferFailed`, ничего не теряется. Шаги: закрыть раунд майнера, если он уже кончился (работа в ещё идущем раунде в эту выплату не входит); рассчитать майнера; перевести `claimable`; `reserved −= claimable`; эмитить `Claimed(beneficiary, amount)`.
- Пыль от округления навсегда остаётся в `reserved`. Это допустимо, инвариант: выплачено ≤ выпущено.
- Других функций вывода, кроме `claim`, нет. Владельца у `HashMine` нет. `receive()` принимает ETH от кого угодно — это и есть пополнение пула.

### 5.6 View для клиента

`currentRound()`, `roundStart(r)`, `challenge(r)`, `minDifficulty(r)`, `roundWork(r)`, `rewardPool()` (баланс − `reserved`), `pending(beneficiary)` (claimable + оценка незакрытого раунда по текущей работе), `minerState(beneficiary)`.

## 6. Браузерный майнер (`web/`)

### 6.1 Стек

Vite + React + TypeScript + viem. Хостинг — статика.

### 6.2 Движки хэширования

| Движок | Где работает | Роль |
|---|---|---|
| JS keccak | main thread | Эталон и перепроверка находок |
| WASM | Web Workers, по одному на ядро | Майнинг на CPU |
| WebGPU (WGSL compute shader) | GPU | Основной движок; возвращает только кандидатов с ≥D нулевых бит |

**Потолок нагрузки — 50% (требование пользователя, 2026-09-14).** Движки работают скважностью: после каждой порции работы простаивают не меньше, чем работали (`intensity` 10–50%, по умолчанию 50, меняется на лету); CPU-воркеров не больше половины ядер. Движки сами измеряют долю занятого времени (`dutyCycle()`), браузерный тест требует ≤ 55% при потолке 50.

Каждого кандидата от GPU и WASM перепроверяет JS-реализация. При первом расхождении движок отключается до перезагрузки страницы, а UI показывает причину.

### 6.3 Сессионный ключ

- При первом запуске страница генерирует приватный ключ и хранит его в `localStorage`. Этот ключ только платит газ за `submit` и `harvest`.
- `beneficiary` — адрес подключённого основного кошелька или адрес, вписанный вручную.
- Сессионный ключ пополняется одним переводом с основного кошелька (один попап). Кнопки: баланс, забыть ключ. **Приватный ключ не показывается нигде** (решение пользователя 2026-09-14 после того, как ключ засветился в скриншоте).
- Награды на сессионный ключ не приходят никогда.

### 6.4 Когда отправлять шары

- Клиент сам выбирает сложность шар: `D = max(minDifficulty(r), D₃₂, D_газ)`.
  - `D₃₂` — наименьшая сложность, при которой хешрейт майнера даёт не больше 32 ожидаемых шар за раунд (одна транзакция на раунд).
  - `D_газ` — наименьшая сложность, при которой ожидаемая ценность одной шары `0.0048 · rewardPool · 2^D / ожидаемая_работа_раунда` не меньше двух стоимостей газа транзакции с одной шарой.
  - Найденные шары клиент копит и сортирует по nonce.
  - Итог симуляции (`sim/RESULTS.md`): доля наград каждой группы равна доле её хешрейта, все группы в плюсе. CPU 23 MH/s получает $0.17 чистыми в сутки при обороте $100k.
- Искать на `D = minDifficulty(r)` нельзя. На полу 20 бит ферма 6 GH/s находит ~3.4 млн шар за раунд, отправить их дороже любого выпуска. Все пропускают отправку, раунды не становятся активными, `minDifficulty` не растёт — тупик (симуляция 2026-09-14, план 03).
- Батч уходит, когда набралось 64 шары или до конца раунда осталось ≤ 20 с.
- Отправка пропускается, если ожидаемая награда батча < 2 × стоимость газа.
  - Ожидаемая награда = `0.0048 · rewardPool · работа_батча / оценка_работы_раунда`.
  - Оценка работы раунда — текущая `roundWork`, линейно экстраполированная к концу раунда.
  - Цена токена в ETH берётся из пула или curve.
  - UI показывает: «невыгодно отправлять: награда X, газ Y».
- `harvest()` клиент вызывает, если ETH в escrow и на `PonsTreasury` в сумме ≥ 0.005 ETH и с прошлого harvest прошло ≥ 60 с. Перед вызовом случайная задержка 0–30 с, чтобы клиенты не дублировали друг друга.

### 6.5 Страницы

- **Mine:** выбор движка, хешрейт, найденные и отправленные шары, таймер раунда, пул наград, ожидаемая награда, pending/claim, сессионный ключ.
- **Stats:** история раундов из событий (работа, выпуск, число майнеров), суточная метрика уникальных `beneficiary`.

## 7. Тестирование

1. **Юнит-тесты (forge):**
   - граница валидности: ровно `D` бит принимается, `D − 1` — нет;
   - порядок nonce;
   - граница раунда: `end − 1` принимается, `end` — нет;
   - `minDifficulty` с пустыми раундами;
   - закрытие раунда, расчёт, claim;
   - донат токена в пул.
2. **Инварианты (forge invariant):** выплачено + claimable ≤ выпущено ≤ поступило; награды майнеров одного раунда пропорциональны работе с точностью до 1 wei на майнера.
3. **Газ-снапшоты:** `submit` с 1, 16 и 64 шарами, `claim`, `harvest` (на форке).
4. **Кросс-реализации:** forge-скрипт генерирует векторы `(beneficiary, challenge, nonce) → h` в JSON. Те же векторы проверяются для JS, WASM (vitest) и WGSL. Работает ли WebGPU в headless-браузере, не проверено; если нет, WGSL проверяется вручную в Chrome.
5. **Форк mainnet (anvil `--fork-url`):**
   - запуск через настоящую фабрику PONS;
   - сделки с тестовых аккаунтов;
   - `harvest` до graduation;
   - доведение до graduation и создания пула;
   - `harvest` после graduation, без свипа оператора и со свипом (`vm.prank` на адрес оператора из §2);
   - миграция с таймлоком.

   **Не проверено**, что anvil нормально форкает Robinhood Chain. Это первая задача плана.
6. **Симуляция параметров (скрипт):**
   - сценарии: «1 ферма 6 GH/s + 1000 браузеров по 50–250 MH/s», «всплеск оборота и затухание»;
   - на выходе: награда на майнера в сутки и доля батчей, отправлять которые выгоднее, чем платить газ;
   - по итогам правится §5.1.

## 8. Выкладка

1. **Testnet 46630.** `HashMine` с пулом в тестнетном ETH; вместо harvest — `TopUp.s.sol` переводит ETH на `HashMine`. Публичный тест майнинга с живыми кошельками.
2. **Mainnet 4663 — только по явной команде «mainnet».** Порядок (ревизия §4): `DeployMainnet.s.sol` (HashMine + PonsTreasury, owner — кошелёк пользователя) → пользователь запускает токен на PONS (пара ETH, tax 2%, buyback off) → `transferCreatorFeeRecipient(token, treasury)` с кошелька → `adopt(token)` → проверка ончейн `getLaunchedToken(token).creatorFeeRecipient == treasury` → сайт переключается на mainnet-адреса (`VITE_CHAIN=mainnet`, `VITE_HASHMINE_ADDRESS`, `VITE_TREASURY_ADDRESS`, `VITE_FEE_ESCROW_ADDRESS`, `VITE_PONS_TOKEN`).
3. Мейннет-деплой можно делать до запуска токена: `HashMine` больше не зависит от адреса токена.

## 9. Риски

1. **Нет оборота — нет наград.** Выпуск 0.48% за раунд (половина пула за сутки) это сглаживает, но не устраняет.
2. **После graduation** комиссии с покупок копятся в самом токене, а в ETH их переводит только оператор PONS. Замер задержки: медиана 2.5 мин, p90 26.7 мин, максимум 5.4 ч. Это касается и собственных выкупов Treasury (exact-input ETH→токен): пока в хуке висит комиссия в токене, Treasury не может свипнуть хук сам (`InternalSwapRequiresOperator`). На практике после graduation почти весь приток комиссий идёт через кипер оператора (проверено на форке 2026-09-14).
3. **Фермы заберут бо́льшую часть наград.** Лимиты на адрес обходятся новыми адресами, поэтому их нет. Малым майнерам помогают только низкий порог сложности и батчи.
4. **Газ.** Сейчас 0.0735 gwei, L1-часть 0. По статье CryptoTimes, льгота Robinhood по газу заканчивается около конца сентября 2026. Рост газа съест мелкие батчи; клиент пропускает невыгодные отправки.
5. **Доверие к PONS.** Владелец фабрики PONS может переназначить получателя комиссий через свой таймлок 3 дня (`CREATOR_FEE_RECIPIENT_TIMELOCK`).
6. **Сэндвичи выкупа** — см. §4.2.
7. **Скорость своего WGSL-шейдера** может оказаться ниже, чем у hashcats (250 MH/s на GTX 1050 Ti по их замеру).
8. **Юридическое.** Токен — мемкоин; на сайте никаких обещаний дохода.
